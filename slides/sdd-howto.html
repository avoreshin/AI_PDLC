§ 01 — основаниячто такое SDD
основания / 01

SDD — это контракт,
а не документация.

Specification-Driven Development документ — машиночитаемая спецификация. Агент читает её как прямую инструкцию. SDD не описывает то, что есть, — он предписывает то, что должно быть.
DOCS

Документация

Описывает текущее состояние. Пост-фактум. Устаревает.

TICKET

Jira-тикет

Описывает задачу. Двусмысленный. Для людей.

SDD

SDD

Описывает контракт: что должно быть, как проверить, чего нельзя.

§ 01 — основаниякогда писать
граница / 02

Когда SDD обязателен.
Когда — избыточен.

Пиши SDD когда

  • Задача передаётся агенту (issue → headless → PR)
  • Risk class ≥ R2 (фичефлаг, auth, payments, infra)
  • Затрагивается контракт API или схема БД
  • Меняется внешне видимое поведение
  • Есть инварианты безопасности / производительности

Не пиши SDD когда

  • Исправляешь опечатку в комментарии (R0)
  • Локальный рефакторинг внутри одного метода
  • Доделываешь свою же фичу за 15 минут
  • Внутренний эксперимент в branch без CI
  • Hot-fix критического инцидента (пиши post-mortem)
Дольше 30 минут или может выполнить агент — пиши SDD. правило большого пальца

step.01 — header
§ 03 · шаг 02 (1/2)goal
шаг
02

Goal — одно предложение, прибитое к стене.

Содержит «что» + «зачем» + границу (фичефлаг, область). Никаких прилагательных типа «улучшить» или «оптимизировать».

✓ ПРАВИЛЬНО 
## Goal
Ввести per-tenant rate limiting на /api/v1/*,
100 req/s по умолчанию, override через
tenant_settings. Под feature flag
`rate_limiter_v2`.

Почему хорошо: конкретно что (rate limit), где (/api/v1/*), сколько (100rps), как настраивается (tenant_settings), как откатить (feature flag).

✕ НЕПРАВИЛЬНО 
## Goal
# вариант 1 — размыто
Улучшить производительность API.

# вариант 2 — слишком общо
Добавить rate limiting в систему.

# вариант 3 — без границы
Защитить API от перегрузки.

Почему плохо: агенту негде остановиться. «Защитить» — где, на каком уровне, на каких эндпоинтах? Без чисел и границ — fail.

step.02 · goal
§ 03 · шаг 02 (2/2)non-goals
шаг
02

Non-goals — то, что намеренно не делаем.

Без non-goals агент расползётся в смежные области. С non-goals — у вас есть контракт, на который можно сослаться при ревью.

## Non-goals

# соседние фичи
- Global rate limit (есть отдельный SDD-043)
- DDoS-mitigation — на уровне CDN
- Rate limit на /admin/* — отдельный scope

# «удобные расширения»
- Динамическая подкрутка лимитов без рестарта
- UI для управления лимитами
- Метрики стоимости запросов в биллинге

# «давайте заодно»
- Изменение схемы tenant_settings
- Рефакторинг middleware пайплайна
- Миграция на новую версию Redis

3 категории non-goals

  • Соседние фичи — то, что выглядит как часть, но имеет свой SDD
  • «Удобные расширения» — то, что агент захочет добавить «пока работает»
  • «Давайте заодно» — рефакторинги в смежных областях

Метрика: если у тебя < 3 non-goals — ты ещё не подумал. Хороший SDD имеет 5–8 non-goals.

§ 03 · шаг 03 · примерыacceptance criteria
Given · When · Then

Хороший AC vs плохой AC.

✓ ХОРОШО 
AC-2  Given tenant T с limit=100rps,
      When  отправлено 150 req/s
            в течение 10 секунд,
      Then  ≥ 500 ответов имеют код 429
            И каждый 429 содержит header
              Retry-After ≤ 1
            И header X-RateLimit-Remaining = 0.
  • Конкретные числа (150 rps, 500, ≤1)
  • Длительность измерения указана (10 сек)
  • Headers названы дословно
  • Все условия в Then — проверяемы
✕ ПЛОХО 
AC-2  Given высокая нагрузка,
      When  превышен лимит,
      Then  система должна правильно
            обрабатывать запросы и возвращать
            подходящие коды ошибок.
  • «Высокая» — сколько? Прилагательное вместо числа.
  • «Правильно обрабатывать» — это не проверяемо.
  • «Подходящие коды» — какие именно?
  • Невозможно сконвертировать в test case.
Тест-имени: def test_ac2_throttle_returns_429_with_retry_after().
Если из AC такое имя не выводится — переписывай.

§ 03 · шаг 04negative cases
шаг
04

Negative cases.

Минимум 2 negative case на SDD. Тест на честность спецификации: если не можешь сформулировать чего НЕ должно случиться — ты не понимаешь поведение.

## Acceptance criteria — negative

AC-4 [negative]  «новый клиент без settings»
     Given tenant T без tenant_settings (новый клиент),
     When  отправлен 1 запрос,
     Then  200 OK (НЕ блокировать как unconfigured)
           И применён default 100rps.

AC-5 [negative]  «фичефлаг выключен»
     Given feature flag rate_limiter_v2 = off,
     When  отправлено 10 000 req/s,
     Then  никаких 429, поведение идентично baseline.

AC-6 [negative]  «медленный Redis не блокирует»
     Given tenant T с limit=100rps,
     When  Redis отвечает с задержкой > 200ms,
     Then  fallback срабатывает на этом запросе
           И запрос НЕ блокируется ожиданием Redis.
Любой инженер скажет, что должно работать.
Только хороший скажет, что должно ломаться. И как. negative-case-first design
step.04 — negative
§ 03 · шаг 05 (1/2)invariants
шаг
05

Invariants — что не двигается.

Свойства, сохраняющиеся после изменения. Каждый инвариант — измеримое утверждение, не пожелание.

## Invariants

▸ Performance
  - p99 latency POST /api/v1/* увеличится не более чем на 5ms от baseline
  - p99.9 latency не вырастет более чем на 10ms
  - throughput на однопроцессном инстансе не упадёт ниже 800 rps

▸ Contract
  - Никаких изменений в схеме ответа /api/v1/* кроме headers (X-RateLimit-*)
  - Никаких новых required-параметров
  - Backwards-compatible с openapi/v1.4.0

▸ Security
  - Никаких новых scopes в IAM
  - tenant_settings читаются только из доверенного источника (БД), не из request
  - Логи не содержат plain rate-limit threshold (только tier name)

▸ Observability
  - Все существующие алерты продолжают работать
  - trace_id сохраняется во всех путях (включая fallback)
step.05 · invariants
§ 03 · шаг 05 (2/2)как выбирать инварианты
методика

Как выбрать инварианты,
а не угадать.

5 источников инвариантов

  1. SLO документ сервиса — каждый SLO становится инвариантом дословно
  2. «Что вас разбудит ночью» — спроси у platform-команды
  3. Existing contract tests — найди их, перечитай: это обещания, которые нельзя нарушить
  4. Threat model — если её нет, время написать
  5. Точки наблюдения клиентов — что кэшируют, на что полагаются

Признаки хорошего инварианта

  • Измерим автоматически — есть метрика или тест
  • Имеет число или формальный предикат — «p99 +≤ 5ms», не «быстро»
  • Привязан к существующей метрике — не «давайте измерим»
  • Будет проверяться в CI — не «вручную»

Признаки плохого инварианта

  • «Не должно деградировать» — без числа
  • «Сохранить надёжность» — без определения
  • «Не сломать существующее поведение» — слишком широко

06

Risk class — где сработает merge gate.

Один из R0…R5. Определяет, какие hooks отработают, нужен ли human approval, какой формат evidence требуется.

classscopeautonomyчто в SDD дополнительно
R0docs, comments, formattingauto-mergeSDD не обязателен
R1tests, local refactor, non-prodauto + post-hooksSDD-lite
R2feature code behind flagagent PR + reviewполный SDD, ≥ 5 AC
R3auth, payments, PII, infradraft + security review+ threat model, ≥ 7 AC, SAST
R4production data, IAM, migrationshuman approval+ rollback plan, separation of duties
R5regulated model / risk logicchange advisory+ regulator audit package

§ 03 · шаг 07manual approval
шаг
07

Manual approval — где обязателен человек.

Явно перечисли моменты, где автоматика останавливается. Approval — именной: кто конкретно подписывает, не «команда».

## Manual approval points

▸ merge в main
  - required review: @security-team
  - не менее 2 approvals
  - все checks зелёные

▸ enable feature flag в prod
  - change advisory ticket
  - presence of rollback runbook
  - on-call notified в #platform-ops

▸ изменение tenant_settings schema
  - migration review by @db-team
  - separation of duties (не автор)

▸ deletion of rate-limit record
  - 4-eyes principle
  - audit log retention 7 years

Где обычно нужен человек

  • Изменения в IAM / RBAC
  • Migrations с DROP / ALTER на больших таблицах
  • Включение фичефлага в production
  • Удаление данных пользователей
  • Изменение секретов в Vault
  • Деплой в financial / health системы
  • Любое R4+ — по определению

§ 03 · шаг 08evidence required
шаг
08

Evidence — что должно быть в bundle.

Список доказательств. Stop hook не закроет задачу, пока всё перечисленное не появится в evidence bundle.

## Evidence required

▸ Tests
  - AC-1..6 в tests/contract/test_rate_limit.py
  - pass@5 ≥ 0.95 на eval-suite rate_limiter_caps
  - pass^5 ≥ 0.80 на regression-suite

▸ Performance
  - benchmark до/после: tools/bench_p99.py
  - delta p99 ≤ 5ms (см. invariants)

▸ Security
  - SAST clean (semgrep, bandit)
  - secrets scan clean (gitleaks)
  - threat model updated в docs/threat-models/rate-limit.md

▸ Resilience
  - redis-down chaos test пройден (tests/chaos/test_redis_down.py)
  - timeout-based fallback подтверждён
Если evidence пуст — задача не сделана.
«Все тесты прошли» не evidence. Имена suite, файлов, метрик — evidence.

SDD-2026-042 целиком.

---
id: SDD-2026-042
title: "Rate limiter for /api/v1/* with Redis + in-memory fallback"
owner: @platform-team
status: ready-for-ai
risk_class: R2
related: [ADR-017, JIRA PLAT-1284]
---

## Goal
Ввести per-tenant rate limiting на /api/v1/*, 100 req/s по умолчанию,
override через tenant_settings. Под feature flag `rate_limiter_v2`.

## Non-goals
- Global rate limit (есть отдельный SDD-043)
- DDoS-mitigation — на уровне CDN
- Динамическая подкрутка лимитов без рестарта
- Изменение схемы tenant_settings

## Acceptance criteria
AC-1 Given limit=100rps, When 100 req/s, Then все 200 OK.
AC-2 Given limit=100rps, When 150 req/s, Then ≥500 ответов 429 с Retry-After ≤ 1s.
AC-3 Given Redis недоступен, When 100 req/s, Then fallback in-memory, rl_fallback_active=1.
AC-4 [neg] Given без settings, When 1 req, Then 200 OK + default 100rps.
AC-5 [neg] Given flag=off, When 10000 req/s, Then никаких 429, baseline.
AC-6 [neg] Given Redis lag > 200ms, When req, Then fallback без блокировки.

## Invariants
- p99 latency POST /api/v1/* +≤ 5ms от baseline
- Схема ответа /api/v1/* без изменений (кроме X-RateLimit-* headers)
- Никаких новых scopes в IAM
- trace_id сохраняется во всех путях (включая fallback)

## Manual approval
- merge в main: review @security-team, ≥ 2 approvals
- enable flag в prod: change advisory ticket
- изменение tenant_settings schema: review @db-team (separation of duties)

## Evidence required
- AC-1..6 в tests/contract/test_rate_limit.py, pass@5 ≥ 0.95
- redis-down chaos test пройден (tests/chaos/test_redis_down.py)
- benchmark p99 до/после (tools/bench_p99.py), delta ≤ 5ms
- SAST + secrets scan clean (semgrep, gitleaks)
- openapi.yaml обновлён (новые X-RateLimit-* headers)
- runbook «как откатить feature flag» в docs/runbooks/

Как писать SDD не в одиночку.

Mob Elaboration — командный ритуал 60–90 минут вместо асинхронного PR-ревью спецификации. Все будущие ревьюеры — уже в контексте.

10 МИН

Контекст

Author читает PRFAQ + ADR вслух.

20—40 МИН

Draft AC

Команда диктует Given/When/Then.

15 МИН

Agent-persona

Кто-то читает «как агент» — ищет дыры.

10 МИН

Negative cases

Чего не должно произойти.

5 МИН

Sign-off

Risk + approval + evidence.

Выход: SDD готов к Mob Construction. Все, кто будет ревьюить или писать код — уже в контексте. ~60–90 мин всего

§ 08 — ревьюchecklist
перед публикацией

SDD готов, если…

Содержание

  • Goal — одно предложение, конкретно
  • Non-goals содержат ≥ 3 пункта
  • Acceptance criteria ≥ 5 (для R2+)
  • Минимум 2 negative case
  • Каждый AC выводится в test name дословно
  • Инварианты измеримы автоматически
  • Risk class соответствует scope
  • Evidence-секция упоминает имена файлов

Качество формулировок

  • Никаких «оптимизировать», «улучшить»
  • Все числа конкретны (100rps, не «много»)
  • Метрики и headers названы дословно
  • Owners — конкретные люди или команды
  • Related ссылки рабочие (ADR, JIRA)
  • SDD прошёл agent-persona reading
  • Все non-goals — категоризированы
Финальный тест: дай SDD незнакомому человеку. За 5 минут не скажет, что надо проверить — переписывай.

§ 09 — антипаттерныspecification debt
антипаттерны

Как не надо писать SDD.

«Документ-тикет»

Симптом: «реализовать рейт-лимитер». Это тикет, не SDD.

Размытый Goal

Симптом: «улучшить производительность». На какой метрике? На сколько?

AC как описание

Симптом: «должен корректно обрабатывать». Невозможно в тест.

Нет negative cases

Симптом: только happy path. Edge cases агент додумает неправильно.

Risk class занижен

Симптом: auth-фича помечена R1, чтобы не ждать security review.

Evidence «всё прошло»

Симптом: Stop hook пропустит, регуляторный аудит — нет.

Specification debt — техдолг, не видный в коде.
Gartner: −25% velocity к 2027 у организаций без SDD.

карточка-памятка

SDD за 60 секунд.

Если только начинаешь

  1. Скопируй шаблон R1 → заполни header (5 мин)
  2. Напиши Goal в одно предложение
  3. Сформулируй 3 happy AC в Given/When/Then
  4. Добавь 1 negative case
  5. Назови файлы test/eval — это evidence
  6. Дай прочитать коллеге как agent-persona
  7. Переведи status в ready-for-ai

Семь правил, которые работают

  • Числа > прилагательные. 100rps, не «быстро».
  • Имена > описания. Конкретные test-файлы.
  • Negative-first. Что НЕ должно случиться — сразу.
  • Owner — человек, не «команда».
  • Risk class +1. Если сомневаешься — выше.
  • 1 AC = 1 тест.
  • Прочитай вслух. Заикнулся — переписывай.
